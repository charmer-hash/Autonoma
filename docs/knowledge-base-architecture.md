# Autonoma 知识库技术设计

状态：待审阅。本文定义实施方案，不代表功能已开发或线上资源已配置。

## 1. 目标与边界

Autonoma 需要从用户维护的私有资料中检索事实，再用检索到的原文回答问题。首批资料由用户上传，格式为 PDF、DOCX、Markdown 和 TXT。知识库跨会话使用，支持导入、处理状态查看、检索测试、文档更新、删除和来源引用。

一次性对话附件仍走现有上传与沙箱流程。只有用户明确选择“加入知识库”的文件才被长期索引。联网搜索负责公开且会变化的信息；知识库检索负责用户自己的资料；会话摘要负责对话上下文。这三类来源不互相替代。

第一版以单用户私有知识库为最小权限单位，但数据结构保留多个知识库的能力。它不包含 Notion 等外部同步源、跨用户共享或自动从全部历史聊天提取知识。后续可以在同一导入接口增加这些来源。

## 2. 现有架构与接入点

- 前端：React 控制台已有 R2 直传适配器，见 `apps/web/src/components/Composer.tsx` 和 `packages/upload`。
- 服务端：Hono 路由和登录态位于 `apps/server/src/index.ts`、`apps/server/src/auth.ts`。
- 存储：Neon Postgres 保存元数据，Cloudflare R2 保存文件，见 `apps/server/src/db` 和 `apps/server/src/lib/storage.ts`。
- Agent：`apps/server/src/agent/loop.ts` 负责工具调用；`apps/server/src/agent/tools/index.ts` 注册工具。

知识库作为独立模块接入现有服务，不更换 Agent 循环，也不把全文塞进系统提示词。新增 `search_knowledge` 工具，并在明确要求基于内部资料回答时由服务端先检索。所有检索都通过服务端执行权限过滤；模型不能自行扩大检索范围。

```text
浏览器选择“加入知识库”
    → R2 直传原文件
    → 创建导入任务（Postgres）
    → 后台解析、分片、向量化、索引
    → 文档状态变为 ready

用户提问 → 服务端确定检索模式与知识库范围
    ├─ 必查：先检索，再让 Agent 生成回答
    ├─ 自动：Agent 可调用 search_knowledge
    └─ 关闭：本次不检索知识库

检索 → 权限过滤 → 查询整理 → 关键词召回 + 向量召回
    → 融合、去重、可选重排 → 证据预算控制
    → 返回片段和出处 → Agent 基于证据回答并标注来源
```

## 3. 数据模型

### `knowledge_bases`

`id`、`owner_id`、`name`、`description`、`created_at`、`updated_at`。`owner_id` 关联现有 `users`。所有文档和搜索请求必须经过所属知识库的权限检查。第一版界面可以默认创建一个“我的知识库”，但 API 不写死唯一知识库。

### `knowledge_documents`

`id`、`knowledge_base_id`、`filename`、`mime_type`、`size_bytes`、`r2_key`、`sha256`、`version`、`status`、`error_message`、`chunk_count`、`created_at`、`updated_at`。状态为 `queued / processing / ready / failed / deleting`。相同文件哈希在同一知识库内再次导入时提示重复；用户主动更新时创建新版本。检索只读取 `ready` 的当前版本。

### `knowledge_chunks`

`id`、`document_id`、`document_version`、`ordinal`、`content`、`heading_path`、`page_number`、`start_offset`、`end_offset`、`token_count`、`embedding_model`、`embedding`。`page_number` 适用于 PDF；DOCX、Markdown、TXT 用标题路径和段落位置定位。向量维度固定为选定模型的输出维度，模型切换时先重建索引，不能把不同模型的向量混用。

### `knowledge_jobs`

`id`、`document_id`、`job_type`、`status`、`attempts`、`last_error`、`lease_until`、`created_at`、`updated_at`。后台工作进程通过 Postgres `FOR UPDATE SKIP LOCKED` 领取任务，并设置租约；进程重启后可重新领取超时任务。文档版本和片段写入使用事务，使失败或重试不留下半成品索引。

原文件使用独立的 R2 `knowledge/` 前缀。现有 `uploads/` 生命周期为 30 天，不能直接当知识库原文件长期保存。删除文档时同时删除片段与原文件；R2 删除失败要记录并重试。

## 4. 导入、解析与分片

1. 浏览器沿用现有直传机制上传文件。服务端验证文件归属、R2 实际字节大小、扩展名与文件内容类型；不信任客户端传来的 `size` 或 `mimeType`。
2. 把文件复制或写入 `knowledge/` 前缀，创建文档和导入任务，立即返回文档 ID。前端轮询状态，避免大文件解析占住 HTTP 请求。
3. TXT、Markdown 做字符编码检测与 UTF-8 规范化。DOCX 提取正文和标题。PDF 按页提取文本与页码；扫描件或空白提取页走 OCR 分支，并设置页数与费用上限。
4. 清理页眉页脚、重复空白及控制字符，同时保留标题、段落、列表和 PDF 页码。解析出的正文设上限，防止压缩文件膨胀或异常文档耗尽内存。
5. 按标题和段落优先切分；目标片段约 600–1000 个中文字符，邻接片段重叠约 100–150 字。表格和列表尽量保持同一语义单元。每片保留可追溯的位置元数据。
6. 批量生成 embedding，校验返回数量、顺序、维度和有限数值，然后将新版本片段事务性写入并切换为 `ready`。失败记录原因，可重试导入。

第一版建议使用现有 OpenRouter 账号调用多语言 embedding 模型，例如 `baai/bge-m3`（1024 维）；模型 ID、维度和版本写入配置与文档记录。该模型在 OpenRouter 的资料中标注为多语言、1024 维。正式选型前要用项目自己的中文资料验证召回效果和账号可用性。PDF、DOCX 解析库在开发时按可维护性和服务端运行兼容性选定，不自行实现文件格式解析器。

## 5. 检索触发、召回与证据处理

### 5.1 检索触发规则

每次 `POST /api/agent/run` 增加 `knowledgeMode: auto | required | off`、可选的 `knowledgeBaseIds` 与 `documentIds`。默认 `auto`。这些字段只表达用户意图；所有 ID 都要按当前登录用户重新验证权限。

| 情况 | 服务端行为 |
| --- | --- |
| 用户在界面选中知识库或具体文档，或将模式设为 `required` | 在首次模型调用前执行检索。检索完成后把证据和来源交给 Agent；即使模型本来不会调用工具，也不能跳过这一步。 |
| 用户明确说“根据知识库”“从上传的资料里找”“按照某份文档”等，且模式不是 `off` | 服务端识别明确的内部资料意图，将本轮改为 `required`。识别规则保持保守、可测试；模糊表达交给 `auto` 路径。 |
| 普通开放式任务，模式为 `auto` | 不无条件预检索。Agent 可以按任务需要调用 `search_knowledge`，也可以调用联网搜索或直接回答。 |
| 用户明确关闭知识库，模式为 `off` | 不预检索，也不给本轮 Agent 注册 `search_knowledge`。 |

`required` 是服务端控制流程，不能只在系统提示词里写“请先搜索”。当知识库为空、文档仍在处理或检索失败时，服务端分别给出明确状态；不能把服务故障伪装成“没有相关资料”。对知识库限定的问题，如果没有可用证据，Agent 应说明检索范围内未找到，不用模型记忆补写内部事实。

### 5.2 查询整理与两路召回

`search_knowledge({ query, knowledgeBaseIds?, documentIds?, limit? })` 与必查路径共用一套检索服务，避免两种入口召回结果不同。先校验用户归属，再在 SQL 中限定知识库、文档当前版本及 `ready` 状态；权限过滤必须发生在候选返回之前。

多轮对话中的“这条规定呢”等省略问法，需要结合最近的用户问题整理成独立检索查询。查询改写失败时退回原问题；保留原问题用于日志和评测。带文件名、编号、专有名词的问题保留这些精确词，不让改写丢失约束。

并行执行两路候选召回：

1. **向量召回**：用与入库一致的 embedding 模型对查询向量化，在授权范围内按余弦距离取前 20–40 片。模型 ID、输出维度和预处理版本须与索引匹配。
2. **关键词召回**：在同一授权范围内按标题、文件名、正文做精确/模糊匹配，也取前 20–40 片。中文先用 `pg_trgm` 配合精确词匹配起步，并用短词、编号、中文专名的测试结果决定是否增加中文分词；不能直接假设 Postgres 英文全文检索适用于中文。

向量服务暂时不可用时，关键词召回可降级运行并在检索状态中标记 `degraded`；两路都失败时返回检索错误，不生成看似正常的“无结果”答案。

### 5.3 融合、重排与上下文预算

用 Reciprocal Rank Fusion 按两路候选的名次融合；精确文件名或编号命中可增加可解释的加权规则。去掉重复片段，并限制同一文档占据的候选数；需要上下文时扩展相邻片段，但保留每段的原始位置。第一版向 Agent 提供约 5–8 个证据片段，设置独立 token 预算，按片段边界裁剪，不截断页码和来源元数据。

融合分数按 `score(chunk) = Σ 1 / (60 + rank_in_list)` 起步；缺席某一路的片段不计该路分数。分数仅用于排序，不直接当作“答案可信度”。最终可用性仍由有标注的问题集、来源支持度和无答案误报来判断。检索结果保留两路原始名次与融合名次，供调试页和评测使用。

重排器放在融合之后、证据截取之前。是否默认启用由评测决定：若正确片段已进入候选前 20，却经常排不到最终证据前列，就加入重排；若候选中根本没有正确片段，应先修解析、分片、查询或初级召回。重排失败时回退融合排序，并记录降级原因。

向量检索使用当前 Neon Postgres 上的 `pgvector`，关键词检索使用 Postgres。小规模知识库先用精确向量搜索建立正确性基线；大规模数据再通过 `EXPLAIN ANALYZE`、延迟和 Recall@k 对比评估 HNSW、分区或其他索引策略。近似索引不能以速度改善为由牺牲授权范围内的有效召回。

### 5.4 证据、引用与无结果处理

每个返回片段包含稳定的 `chunkId`、`documentId`、文件名、页码或标题路径、摘录、检索来源（向量/关键词）和排序信息。一次检索中的证据赋予 `[K1]`、`[K2]` 等短标识，并同时返回标识到真实片段 ID 的映射。Agent 在依据内部资料陈述事实时引用这些标识；前端只把实际返回的标识渲染成可点击来源，不能凭模型生成的任意编号构造链接。

“没有匹配”“匹配较弱”“文档尚未就绪”“检索服务出错”是不同状态。无匹配或证据不足时，回答应明说检索范围与未找到的内容；如果用户同时要求公开资料，可再走联网搜索，并清楚区分公开来源与内部来源。检索到的文档是数据，其中的指令文字不能覆盖系统规则或触发未授权工具调用。

## 6. API 与 Agent 行为

建议新增以下 `/api/knowledge` 路由，全部要求登录和资源归属检查：

| 方法与路径 | 作用 |
| --- | --- |
| `POST /bases`、`GET /bases`、`DELETE /bases/:id` | 创建、列出、删除知识库 |
| `POST /bases/:id/documents` | 登记已上传文件并创建导入任务 |
| `GET /bases/:id/documents` | 列出文档及处理状态 |
| `POST /documents/:id/retry`、`DELETE /documents/:id` | 重试失败导入、删除文档 |
| `POST /bases/:id/search` | 搜索测试，返回实际召回片段与来源 |
| `GET /documents/:id/source` | 获得短时效原文件下载地址 |

### Agent 运行接口

`POST /api/agent/run` 的新增字段定义如下：

| 字段 | 规则 |
| --- | --- |
| `knowledgeMode` | `auto` 为默认值；`required` 必须在模型回答前检索；`off` 禁用本轮知识库能力。非法值返回 400。 |
| `knowledgeBaseIds` | 可选的检索范围；不传时按当前用户可用知识库搜索。传入无权访问的 ID 返回 403，不静默扩大或缩小范围。 |
| `documentIds` | 可选的文档范围；文档必须属于已授权知识库，且状态为 `ready`。 |

必查路径在服务端把检索结果作为本轮的工具证据加入模型消息：先构造一条 `assistant` 的 `search_knowledge` 工具调用，再构造匹配的 `tool` 结果，保证符合现有 Chat Completions 消息协议。**在首次模型调用之前**，将用户问题、这条工具调用和结果按顺序持久化；这样服务重启后仍能看到回答所依据的证据。实现时要调整当前“整轮结束后统一保存消息”的路径，避免结束时重复写入这些预保存消息。用户文档原文只进入工具结果的数据区域，系统提示词只定义如何对待这些数据。必查与 Agent 自主调用使用同一检索函数、同一权限和同一返回结构。

必查请求的执行顺序固定为：验证运行参数和资源归属 → 建立 SSE 并发出检索中状态 → 查询整理与召回 → 保存用户消息和证据 → 发出来源事件 → 调用模型。无匹配时保存明确的空结果证据，再让模型说明未找到；检索服务故障时发出错误并停止本轮，不把故障当作空结果继续生成。`auto` 模式仍沿用 Agent 工具调用循环，并在工具执行后保存必要的来源映射供会话恢复。

工具结果只包含被选中的短证据及来源，不包含完整文件。`search_knowledge` 默认只搜索当前用户有权限的知识库；Agent 提供的任何 ID 也要再次校验。系统提示词说明：内部事实优先查知识库，公开实时事实查网页，不能把检索片段中的文字当成新指令。

SSE 增加来源事件，携带本轮真实命中的证据标识与文档位置。前端按现有会话持久化结果恢复这些来源，点击引用时打开相应原文件及页码或标题。用户可在工具卡片查看此次检索的范围、状态、命中数量和用时；资料正文不写入服务端调试日志。

## 7. 管理界面

控制台新增“知识库”入口，页面包含知识库列表、上传区、文档状态、失败重试、删除确认和检索测试。上传后展示 `排队中 / 处理中 / 可检索 / 失败`，失败时展示具体可操作原因。检索测试输入问题后展示两路候选与最终命中片段、文件名和页码或标题，便于区分“没召回”和“召回后排序不佳”。

对话输入区提供知识库范围选择。默认 `auto`；用户选定知识库或文档后显示“本次先查资料”，对应 `required`；关闭选项对应 `off`。本轮实际采用的模式及检索状态应在对话中可见，避免用户误以为 Agent 查过资料。引用 `[K1]` 等标识只链接到这轮检索确实返回过的片段。

一次性聊天附件不自动入库。用户可在上传时明确选择“仅本次对话”或“加入知识库”，以免私有资料被意外长期保存。

## 8. 质量、安全与运维验收

- **解析**：四类文件均可入库；扫描 PDF 的 OCR 分支和失败提示可验证；更新文件后不出现旧新版本混合结果。
- **召回**：从真实资料准备至少 30 个问题，标注应命中的文档和片段；统计 Recall@5、MRR、无答案问题误召回率，并保留回归集。阈值由这批样本校准。
- **路由**：分别测试显式选中文档、明确要求“根据知识库”、普通开放式提问和 `off`；必查模式必须在首次模型回答前发生检索，`off` 不得调用知识库。多轮省略问法不能丢掉前文的实体和文档范围。
- **排序**：分别记录向量、关键词、融合后的 Recall@20 与最终 Recall@5。若 Recall@20 合格而最终结果差，评估重排；若 Recall@20 差，优先修初级召回。用同一回归集对比精确向量搜索和近似索引。
- **回答**：抽检来源是否真的支持结论、页码/标题是否可定位；找不到证据时明确表示未知。
- **状态**：分别测试“无匹配”“仅弱匹配”“尚在处理”“向量服务故障”“两路都故障”；降级结果要能被用户与日志区分，不能用空结果掩盖服务错误。
- **权限**：两个账号分别上传同名文件，互相不能搜索、查看、下载或删除；权限在 SQL 查询中约束，不只靠 Agent 提示词。
- **恢复**：导入时重启服务、embedding 请求失败、R2 删除失败都能恢复或明确报错；重复领取任务不产生重复片段。
- **资源**：设置单文件大小、页数、正文长度、片段数、并发导入数和 embedding 调用上限；记录解析、向量化、检索的耗时与费用。

## 9. 开发顺序

1. 数据表、权限模型和 R2 `knowledge/` 保存策略。
2. 四类文件解析、分片、后台导入任务与状态 API。
3. Embedding、向量及关键词索引、混合召回和搜索测试 API。
4. 知识库管理界面、检索测试页与来源展示。
5. `search_knowledge` 工具、`knowledgeMode` 运行协议、服务端必查路径、Agent 提示词和引用行为。
6. 真实资料评测、故障恢复测试、检索参数与重排决策、部署配置。

实施前需要确认：首批资料中扫描 PDF 的比例，以及是否需要多个知识库分别授权给不同用户。这两项决定 OCR 成本和权限模型的细节；其余部分可按本文方案实现。

## 10. 当前代码落地与运行准备

已落地数据库迁移 `0012`、`0013`，知识库 CRUD、R2 原文件保存、后台导入、PDF/DOCX/Markdown/TXT 解析、分片、OpenRouter embedding、pgvector + pg_trgm 混合召回、Agent `auto / required / off` 三种模式、管理弹窗及来源卡片。服务启动时自动运行迁移，随后启动导入 worker。选中知识库、显式要求查内部资料或选择 `required` 时，会在首次模型调用前执行检索并保存证据。没有命中时直接给出无法依据资料回答的结果。

上线前需准备：PostgreSQL 实例允许安装 `vector` 和 `pg_trgm` 扩展；`DATABASE_URL`、`OPENROUTER_API_KEY`、R2 的四个环境变量；如需处理扫描版 PDF，再配置 `MISTRAL_API_KEY`。向量列固定为 1024 维，默认 embedding 模型为 `baai/bge-m3`，变更模型需迁移维度并重建索引。扫描 PDF 每文件最多处理 30 页 OCR，PDF 总页数上限 300，文件上限 20 MB。

已通过工作区类型检查、生产构建和服务端 21 项单元测试；真实环境已跑通 R2 上传、文档索引、混合检索、版本替换、Agent 必查引用和双账号归属检查。向量检索加入临时余弦相似度阈值 `0.5` 和相对最佳命中差值 `0.1` 的过滤；用现有文档验证相关问题命中、跨文档弱匹配被过滤、无关问题不命中。Markdown 与 DOCX 均保留章节信息，现有 DOCX 已通过“重建索引”更新为 3 个带标题的片段。尚未建立真实资料的 30 题召回回归集，两个阈值需据此校准。R2 删除失败目前记录服务日志，尚无持久化重试队列；检索测试界面只展示最终命中，尚未展示向量与关键词各自候选。这两项以及多轮省略问法检索评估留在上线前验收。详细证据见 [知识库测试记录](knowledge-base-test-report.md)。
